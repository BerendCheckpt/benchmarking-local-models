## Summary

- **When Qwen3.8 answers, the answers are mostly usable.** 148 of 232 turns produced an answer. They average **2.11 out of 3**, and 74% of them score 2 or higher. Simple lookups, greetings and scope questions, Labelizer objects and issue drafting are often as good as Claude's. On 15 items they were better.
- **36% of turns produced no answer at all.** 62 turns used the agent's whole 600 s budget and came back with "I ran out of time" (average score 0.13). Another 21 hit the 32k output-token limit, and 1 was a network timeout. No answer is the single biggest cost in this run, bigger than wrong answers.
- **The headline weighted score is 39%.** That counts every turn, weighted by risk (see Methodology). The answered turns alone score 66%.
- **The setup worked against the model on code and FDS questions.** The `claude-agent-local` container has **no volumes mounted**, so the repo mirror (`/srv/repos`, which holds the plugin source, FDS documents and the Layout Designer manual) did not exist. Questions that need it score 22% weighted. Without them the run scores 51%. Before comparing models on those questions, mount the mirror. That is a setup problem, not a model weakness.
- **By persona:** developers (67%) and operations staff (54%) are served best. Requirement analysts and support staff come out lowest (32% each), and they ask the questions where a wrong or missing answer costs most.
- **Behaviour is safe.** The model never created a GitHub issue without a "yes", refused write actions correctly, and was honest about attachments and access it didn't have. There were 9 hallucinations, mostly in turns where it used no tools at all.

## Methodology

Each answer was judged on three things you asked for: what the agent can access, what kind of question it is, and who asked it. Five parallel reviewers each scored a batch with the same rubric. I then checked their findings against the raw data and the agent's configuration.

### 1. What the agent can access

The answer is judged against what was **actually reachable in this replay**, not against an ideal agent.

| Access | Reachable in the replay? |
|---|---|
| Back Office API (`bo.py`: retailers, orders, PoCtrlNo, layouts, products, ticket centers) | yes, as the benchmark user, QA |
| Retailer Integration API (`ri.py`: plugins, deployments, jobs, lookups) | yes |
| Plugin source code, FDS documents, Layout Designer manual (repo mirror) | **no**: no mirror mounted in `claude-agent-local` |
| Labelizer skill references | yes (the skill's own notes, which are older than the manual) |
| GitHub issue tool (`request.py`) | yes, propose only until the person says yes |
| Attachments (screenshots, PDFs, order files) | **no**: the JSONL has question text only |
| Earlier turns of the same session | yes, the session is replayed turn by turn in one agent session |
| Logs, databases, servers, the web | no, for both the original agent and the replay |

Every question was marked as **answerable** `full`, `partial` or `no` in this replay. An item marked `no` gets full marks if it says clearly what is missing and offers the best next step. Guessing scores 0.

Other caveats used in judging:
- QA data can have changed since the original answer.
- The replay runs as a different user, so permissions may differ.
- Claude's answer is a reference, not ground truth.

### 2. Score per answer (0–3)

| Score | Meaning |
|---|---|
| 3 | Correct and as useful as the reference, or better. For unanswerable items: states the limit and gives the best next step |
| 2 | Mostly right, with small gaps. The person can work with it |
| 1 | Vague, partly wrong or off-target. The person has to ask again |
| 0 | No answer, wrong on the essential fact, made-up data presented as fact, or an unsafe action |

### 3. Weight per answer

The weighted score is `Σ(weight × score) / Σ(weight × 3)`. The weight multiplies three factors.

**a. Question type: how much a wrong answer costs**

| Question type | Weight | Why |
|---|---|---|
| troubleshoot, implementation-logic | 3 | Production problems and business rules. A wrong answer ends up in a fix, an FDS or a PBI |
| data-lookup, labelizer, request-drafting, feasibility-estimate | 2 | Concrete facts or work items that people act on |
| how-to | 1.5 | Usually easy to check by trying it |
| follow-up | 1 | Carries little new content of its own |
| general | 0.5 | Small talk, meta questions, scope |

**b. Persona: how hard it is for the asker to spot a wrong answer**

| Persona | Weight | Why |
|---|---|---|
| support, operations | 1.25 | Pass answers on to customers, and can't read code or APIs |
| requirement-analyst | 1.15 | Paste answers into FDSs and PBIs, and partly check them |
| layout-designer, unknown | 1.0 | See the result straight away in the designer |
| developer | 0.9 | Can check the answer in code |

**c. Answerability: so unfixable setup gaps don't dominate**

| Answerable | Weight |
|---|---|
| full | 1 |
| partial | 0.75 |
| no | 0.5 |

Questions don't record who asked them. The persona is inferred from the wording and from the rest of the session. For example, one session says "so that RAs like me can query the business rules".

## Findings

### 1. The time budget, not the model's knowledge, decides most scores
- The 62 out-of-time turns show a pattern: the model keeps searching (13 to 58 tool calls) and never writes up what it already has.
  - In #98 and #100 it had already found ERAM VETIR before it ran out of time.
  - In #202 it had already rendered the preview.
- Hardest hit:
  - **support troubleshooting**: 11 of 19 turns
  - **implementation-logic**: 10
  - **data-lookup**: 13
  - **layout-designer how-to and Labelizer**: 18 layout-designer turns in total
- Answered turns used 4.5 tool calls on average. The productive range for this model is short.

### 2. Once a session hits the token limit, every later turn fails too
All 21 token-limit failures fall in 5 sessions. After the first hit, almost every following turn in that session hits it again:

| Session | Turns | Pattern (`.` ok, `T` token limit) |
|---|---|---|
| `c68fc237` | 18 | `..........TTTTTTTT` |
| `df66f031` | 15 | `....TTTTTTT...T` |
| `b22dd127` | 22 | `..................TTTT` |
| `cfa9aaca` | 2 | `.T` |

Some of these were trivial, such as "heb ik een github account?" (do I have a GitHub account?). So it is the resumed session's state, not the question, that triggers it. Starting a fresh agent session after a token-limit error, or raising `CLAUDE_CODE_MAX_OUTPUT_TOKENS`, would recover most of these 21 turns.

### 3. Code and FDS questions were set up to fail
`docker inspect claude-agent-local` shows no mounts, so the mirror the system prompt points to (`/srv/repos/...`) does not exist. The effects:
- The model says honestly that it can't read the plugin code or the FDS (#108, #198, #206). It doesn't make up rules, but it can't get past a score of 1.
- In the SkinKandy follow-ups (#35–37) it claimed the code was unreachable without trying, then gave design advice that was partly wrong. One suggestion was a database counter in a plugin that has no state.
- Questions that need the mirror average 0.81. **Re-run these with the mirror mounted before drawing conclusions about requirement-analyst use.**

### 4. Missing attachments: honest when it doesn't start digging
- **Good:** when it doesn't call tools, it asks cleanly for the error text or screenshot (#2, #18, #135, #160, #230).
- **Bad:** when it does start digging, it fights the `sheet.py` path guard or guesses repo names until time runs out. The SkinKandy "why does this file fail" question was asked 7 times (#24, #75, #93, #96, #99, #102, #185) and never answered. Yet the rule (CheckPrices: a blank GBP or SGD price) could have been explained from the question text alone.

| Item | Error |

| PoCtrlNo 417749805 (#1, #13, #59, #94, #104) | "Not in QA", where Claude found it under ERAM VETIR, order 0014999JR, status 102 REPLACED. Data drift is unlikely: other replies in this same run (#98, #100) found ERAM VETIR before timing out |

| #158, #159, #193 | Misread short Dutch questions: "items" read as jobs, "Toon" read as a person's name instead of "show" |

### 6. Hallucinations come from answering without tools
There are 9 in total:
- #43 and #15 (the "Continue from where you left off" turns) invent topics nobody raised: a Gekas issue in one, an Intersport order in the other.
- #217 and #219 say "what I saw in back office" with an empty tools list.
- #67 says "staat in de code" ("it's in the code") without checking.

### 7. Where it matches or beats the reference
15 items are marked better than expected. Examples:
- **#157, #91, #92:** fetched the RI job catalog and listed the RFID/EPC feedback jobs with their status. Claude got a 403 there.
- **#89:** Pepco plugin version 2026.8.27.44. Claude failed on a missing scope.
- **#125:** found "FRF mapping document" in an FDS reference instead of saying "unknown term".
- **#227, #228:** found the BO field `localsupco` shown as WarehousePackNo, which Claude's code-only search missed.
- **Exact matches:** #26 (1587 retailers in QA), #69 (24 C&A ticket centers), #195 (Jennyfer setup), and the Labelizer paste-ready objects in #25, #83, #84, #119, #122 and #153.

### 8. Language
- Dutch questions score about the same as English ones (1.44 vs 1.37 mean).
- 10 replies were in the wrong language or had garbled Dutch. Every out-of-time message is in English, even when the question was in Dutch.
- One reply had a stray Chinese token (#72).

## Recommendations

| # | Action | Expected effect |
|---|---|---|
| 1 | Mount the repo mirror (`/srv/repos`) in `claude-agent-local` when the benchmark recreates it | A fair score on 67 code/FDS/manual items |
| 2 | Start a fresh agent session after a token-limit error, or raise `CLAUDE_CODE_MAX_OUTPUT_TOKENS` | Recovers most of the 21 empty turns |
| 3 | For local models, have the agent stop searching earlier and write up what it has. For example, a smaller tool-call cap or an earlier wrap-up than 600 s minus the reserve | Turns many of the 62 timeouts into partial answers, which the data already supports |
| 4 | Have the out-of-time message answer in the question's language | Fixes the language issue in finding 8 |
| 5 | Record the asker's role (or BO user group) in the Hanuman export | Lets later reports use the real persona instead of an inferred one |
| 6 | Keep the duplicate questions but report them separately | They show re-asks; a stable model should score the same on each copy |

## Limitations

- One reviewer per item, with no second opinion. Borderline 1/2 and 2/3 scores could shift by about ±0.2 in the means.
- The persona is inferred, not recorded.
- The reference answers are from Claude at the original time, and QA data may have changed since.
- The weights are a judgment call. Unweighted means are shown everywhere next to them.
